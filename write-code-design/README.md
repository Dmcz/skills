# 代码设计文档编写 Skill

`write-code-design` 用于编写或修订代码设计文档和技术 RFC。目标是让工程师理解要改什么、为什么这样设计、有哪些后果，以及哪些问题仍需决定。

文档深度随任务规模变化，具体架构和实现方式由需求、现有代码及项目约束决定。编写或实质修订时，按需要整理章节、文档文件职责和层级，并说明影响设计的代码组织；局部润色保持范围。配套行为评测案例用于检查实际选择、输出和文件操作。

生成的设计文档默认使用中文；用户明确指定语言或修订已有其他语言文档时，遵循实际要求。代码标识符、API 名称和资料标题保留原文。

## 规则说明

### 先明确问题和交付方式

从已有对话和材料提取读者、问题、目标、范围与约束。已经提供的信息直接使用；缺失信息会实质影响方案时再提出集中、明确的问题。可以保持未决的事项写明影响，不补造答案。

讨论时在对话中给出内容；用户要求保存或编辑时再写入相应文档。文档编写、代码实现、运行检查和 Git 操作分别遵循用户授权与项目要求，不因调用这个 skill 自动串成完整开发流程。

### 以现有代码和材料为依据

涉及已有项目时，先查看影响本次改动的代码、接口和项目约定。只修订措辞时，查看相关上下文即可。现状描述需要有依据；建议方案、假设和未决问题在可能引起误解的地方明确区分。

不能虚构性能结果、兼容性保证、负责人或审批状态。关键外部 API 或平台行为存在不确定性时，核对权威资料。

### 遵循格式优先级

用户明确要求优先于 skill 的默认规则；遵循适用的项目约定，并保留已有文档的格式惯例。没有指定或既定格式的新文档，才使用本 skill 的默认元数据和引用标记形式。

窄范围编辑不顺带统一全文格式、补充元数据或移动状态标记。例如，已有 RFC 使用 `## [Accepted] Cancellation`，只润色段落时应保留这个标题及无关内容。

### 按需要整理结构、文件职责和层级

组织判断统一定义在 [design-guidelines.md](references/design-guidelines.md#document-structure-and-file-responsibilities)。新建文档、实质修订或整理相关设计文件时，检查章节和文件边界；重复、职责混杂、细节层次不一致或新增内容遮蔽关键决定时，可以在范围内调整。用户指定固定结构时遵循该要求，局部润色保持受影响的上下文。

章节围绕读者需要理解和决定的问题组织；先说明问题和总体方案，再展开依赖这些内容的细节。多文件协作时说明各文件的读者、用途和范围，按需要区分总览、变更方案、共享契约、模块细节和历史决策。共享定义有权威位置，其他文件通过链接引用；冲突需要依据或明确待决事项，历史决定的来源与状态保留。

总体设计解释系统边界和共享决定，局部设计说明所属模块及其如何满足共享约束。文档层级和代码架构分层分别服务于阅读与实现判断，层级数量按内容决定。小而完整的设计可以留在一个文件；职责、读者、复用或维护需要足以支持拆分时，再建立相关文件和导航。拆分超出交付范围时提出建议，讨论稿继续在对话中交付。

结构调整后检查受影响的目录、导航、链接和锚点，以及要求、依据和决策状态是否完整保留。模板中的关联说明和职责表是可裁剪的示例，不增加固定章节或文件要求。

### 记录日期、文档状态和实现情况

使用本 skill 默认格式新建独立设计文档时，在标题附近记录首次整理日期、最近一次实质更新日期、文档状态和实现情况。字段名及标签统一定义在 [design-guidelines.md](references/design-guidelines.md#document-metadata-and-annotations)，不依赖读取模板。例如：

```markdown
- 整理日期：2026-09-30
- 更新日期：2026-10-01
- 文档状态：设计讨论记录
- 实现情况：尚未实现
```

这些日期仅为格式示例，每份文档按实际情况填写。修订时保留首次整理日期；设计、决策或说明有实质修改时更新日期。未知的历史日期省略或写明未知。

文档状态说明文档性质或评审状态，实现情况说明已核实的代码进展。代码情况没有核实时填写“未核实”，不从讨论状态推断是否已经实现。修订已有文档时遵循其约定格式。

### 使用状态和依据标记

使用默认格式时，需要区分状态的设计事项在章节标题下、正文前使用 Markdown 引用，前后留空行，标题本身不加状态标签。已有文档采用其他形式时遵循其约定。

- **已确认**：用户明确确认，或项目中仍有效的已接受决策所建立的设计约定，不代表已经实现或验证通过。
- **建议**：已经提出但尚未确定采用的方案。
- **待定**：尚未确定的接口、行为或实现方式。
- **暂缓**：当前阶段不实现，未来出现具体需求时再设计，不代表已承诺实施。
- **调研事实**：根据官方资料或指定版本 SDK 的静态声明确认的信息。它是依据标记，与方案是否确定属于不同维度，不代表本包已经实现或验证相应行为。

助手先前提出的建议、未被接受的草稿和已被取代的记录，不能作为确认依据。关键决策按需链接确认来源或已接受记录；状态或有效性不明时说明不确定性，不悄悄改动已有决策状态。现有代码可以证明当前行为，不能证明一项拟议改动已经获批。

```markdown
### 缓存归属

> 状态：已确认

缓存由 Repository 持有。

### SDK 取消接口

> 状态：建议
> 依据：调研事实，参见 [官方文档](资料链接)，SDK 版本：具体版本。

说明已确认的接口信息，以及建议采用的方式。
```

调研依据注明资料来源及相关 SDK 版本；只陈述资料信息的章节可以仅写依据行。无需给每个段落加标签，同一章节包含不同状态时，在相应小节或具体事项分别标记，避免一个章节标记覆盖不同状态。

### 解释职责、交互和选择理由

说明哪个组件负责行为、持有状态或执行副作用，以及依赖方向和一条关键流程。文件拆分本身不代表职责已经清楚。抽象和分层需要解决当前的具体问题，并说明引入成本。

代码组织影响设计时，把重要职责对应到实际或拟议的模块、文件、接口和依赖，说明现状与改动。架构分层说明各层职责及允许的依赖方向。现有文件职责混杂且影响本次改动时，可提出有理由和成本说明的局部拆分或迁移；遵循项目已有模式，保留无关代码组织。

存在真实选择时，按相同标准比较可行方案，说明推荐理由、代价和局限；不凑方案数量。项目已有决定在窄范围修订中保持稳定，实质修改需要明确指出。

### 按改动规模补充细节

小改动可以用少量段落说明问题、方案、理由和验证。多个组件、共享接口或复杂决策需要更多细节。接口、状态、失败、取消、并发、迁移等内容，仅在影响本次设计时展开。

模板是起点，已有项目结构和用户提供的模板优先。图表或示例要解决具体理解问题；实现顺序仅在说明依赖或迁移时展开。

### 保留语义，使用具体表达

润色时保留条件、例外、时序、数量和失败语义。明确执行主体，统一术语，用实际行为解释抽象评价。段落围绕一个中心展开，结论后连接依据和影响。

标题、列表、代码块、链接和表格保持一致的 Markdown 写法。英文规则应用于中文表达时，不机械套用英文拼写和标点习惯。

### 使用外部格式与写作资料

当前 skill 参考两份资料，分别负责格式和表达：

- **markdownlint**：通用 Markdown 格式约定和静态检查。项目已有配置时，按其配置选择规则，包括行长限制。
- **writing-clearly-and-concisely**：借鉴明确主体、具体表达、连贯段落和减少冗余等跨语言原则。中文使用中文语法和标点，保留必要的条件和不确定性。

设计文档继续默认使用中文，模板和 README 使用中文，Agent 指令与参考规范使用英文。英文资料不改变设计文档的输出语言。

日常写作使用本地规则，遇到规则需要澄清时再查阅相关资料，不要求每次完整阅读两份资料，也不要求另行安装或调用写作 skill。工具已可用且项目要求允许时，对修改的 Markdown 文档运行项目配置的 markdownlint 检查；工具不可用时做本地格式检查，不宣称已运行 markdownlint。安装工具或修改检查配置应属于用户请求的范围。

### 区分验证计划与验证结果

验证思路需要对应目标行为和重要不变量。计划执行的检查、已有证据和真实完成的检查分别表述。没有运行测试、没有评审通过或没有独立读者测试，就不宣称这些结果。

交付前从未参与对话的工程师视角检查：问题和推荐理由是否清楚，各处职责与流程是否一致，关键结论是否有依据，待决事项会阻塞什么。完成稿删除模板提示和意外占位内容，真实未决事项保留并说明。

新文档或大幅改写的文档保存后，检查实际保存的文件，确认位置和最终内容。局部修订检查差异或对照原文确认改动及无关内容的保留。保存或检查失败时说明限制，不宣称已完成交付。交付已保存的文档时提供文件链接，并简述实质变化、待决问题和实际检查。

## 使用示例

- `用 $write-code-design 为这个模块的状态管理重构起草中文设计文档，结合现有代码说明职责和取舍。`
- `用 $write-code-design 修订这份 RFC，保留已有决定，补充接口兼容性和失败流程。`
- `用 $write-code-design 整理 docs/design/ 中这组设计文档，明确总览、共享契约和模块设计的职责，更新受影响的链接，保留既有决定。`
- `用 $write-code-design 把已确定的方案整理成文档，先在对话中给出草稿。`

## 后续维护

行为评测案例见 [behavior-cases.md](evals/behavior-cases.md)。当前十二个场景覆盖新文档保存、局部润色、仅讨论、已有英文格式、缺少源码、挑战旧决策、未确认的助手建议、直接修复代码时不触发，以及单文档结构整理、多文档职责与权威定义、代码职责与分层、受限范围内的结构修订。

评测在明确请求时执行，每个案例使用新对话和独立临时工作区。执行者接收请求与原始材料，评测者保留通过标准；分别记录技能是否正确触发，以及实际输出、操作和文件差异是否符合要求。结构检查通过或读过案例，都不代表行为评测通过。

用真实使用中出现的问题补充案例，优先修正有证据的歧义或遗漏。架构规范、中文表达偏好和项目模板逐步补充；每条新增规则应说明它改变了什么判断，避免不断堆积通用建议。
