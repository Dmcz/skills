# Skills

集中维护跨项目复用的个人 Agent Skills 和项目 Agent 指令。具体任务、输出要求和平台依赖由各技能或指令文件说明。

## 技能目录

| Skill | 用途 | 目录 |
| --- | --- | --- |
| code-design-and-implementation | 围绕行为、职责、接口、并发和生命周期进行只读代码分析、设计讨论、代码审查及已确认方案的实现；实现任务包含必要测试。普通语法解释、纯措辞或格式编辑、拼写、简单命名、简单说明注释和机械修改不触发，需要判断行为或契约的注释任务仍触发。审查仅静态只读，测试代码审查也遵循此模式；组合审查与修复或运行验证的请求先按通用规则确认本轮任务类型。 | [code-design-and-implementation/](code-design-and-implementation/) |
| unit-testing | 以单元测试设计、编写或改进为主要产物，围绕行为契约、独立预期值、依赖替身和确定性异步时序编写有效测试；不强制 TDD。独立补测试不自动授权修改生产代码，运行遵循目标项目限制；单纯运行测试不触发编写流程。 | [unit-testing/](unit-testing/) |

| document-confirmed-design | 编写或维护已确认设计的正式说明，记录概念、数据关系、职责、契约和后续方向，不新增设计决定。 | [document-confirmed-design/](document-confirmed-design/) |

## Agent 指令

根目录的 [AGENTS.md](AGENTS.md) 用于维护本仓库；`agents/` 下提供两层可复用指令：

- [通用指令](agents/AGENTS.md)：跨项目的个人默认约定，包括授权范围、沟通与决策、证据使用、技能选择和验证结果报告，安装到 Codex 的全局指令位置。
- [Swift 项目指令](agents/swift/AGENTS.md)：目标项目的文档布局、Swift 工程约定、UI 文案、视觉审查和验证限制，安装到目标项目根目录。

Codex 先加载全局指令，再加载从目标项目根目录到当前工作目录的项目指令；项目中的更具体约定覆盖冲突的全局约定。Swift 项目指令与通用指令配合使用：只复制或软链 Swift 文件到目标项目，不会自动加载本仓库中的 `agents/AGENTS.md`。

以下示例中的 `/path/to/skills` 均需替换为本仓库的实际路径。

### 安装通用指令

以下示例使用默认的 Codex 全局目录 `~/.codex`；如果设置了 `CODEX_HOME`，请将该目录替换为其实际路径。先创建目录，再选择软链或复制中的一种方式：

```bash
mkdir -p ~/.codex

# 软链：共享本仓库中的通用指令
ln -s /path/to/skills/agents/AGENTS.md ~/.codex/AGENTS.md

# 复制：独立维护全局指令
cp -i /path/to/skills/agents/AGENTS.md ~/.codex/AGENTS.md
```

如果已有全局 `AGENTS.md`，先检查并合并需要保留的约定。全局目录中的非空 `AGENTS.override.md` 会优先于 `AGENTS.md` 加载。安装后启动新的 Codex 会话，使指令重新加载。

### 安装 Swift 项目指令

安装通用指令后，在目标 Swift 项目根目录选择一种方式；如果已有项目 `AGENTS.md`，先检查并合并项目原有约定：

```bash
# 软链：共享本仓库中的源文件
ln -s /path/to/skills/agents/swift/AGENTS.md AGENTS.md

# 复制：在目标项目中独立维护
cp -i /path/to/skills/agents/swift/AGENTS.md AGENTS.md
```

两层指令都遵循相同的维护方式：通过软链编辑安装位置的 `AGENTS.md` 会修改本仓库中的对应源文件；复制后的文件独立于源文件，后续更新由使用方维护。

指令中的设计索引、项目结构和应用架构引用面向目标项目，用于按需定位和理解相关内容，无需在本仓库中提供对应文档。项目业务约定由目标项目维护。

## 公共编写约定

根目录的 [AGENTS.md](AGENTS.md) 定义维护本仓库时的 Agent 规则；本 README 解释这些约定并提供使用入口。各技能的执行规则由其 `SKILL.md` 和引用的资源定义。

- 每个技能使用独立目录，目录名与 `SKILL.md` 中的 `name` 一致，采用小写字母、数字和连字符。
- `SKILL.md` 是必需文件；参考资料、脚本、模板和评测案例按实际需要添加。
- Agent 指令、参考规范和评测说明使用英文；供维护者阅读的 README 使用中文。示例材料、模板和生成内容的语言遵循具体技能及用户要求。
- 单个技能应能独立使用，所需规则保存在技能内部，避免依赖仓库根目录的说明文件。
- 各技能的 README 按维护需要提供，用于说明和示例；执行规则的修改应同步检查相关说明。

## 使用与维护

在 Codex 中，可以通过 `$技能名` 显式调用，例如：

```text
用 $draft-software-design 为当前模块起草设计手稿，先在对话中给出方案和待讨论的问题。
```

工作流按用户要求的产物区分：普通代码分析和方案讨论按适用范围使用 `code-design-and-implementation`；明确要求起草或修订设计手稿、RFC 或提案文档时使用 `draft-software-design`。手稿可以先在聊天中交付，起草不自动授权保存文件；已授权保存且没有指定路径时，放在项目设计区的 `drafts/`。手稿只在明确关联的讨论、首次实现或施工任务中参考；正式文档用于查阅有效约定，二者按用途而非篇幅区分。写手稿所需的代码阅读属于该文稿任务，不因此自动叠加代码工作流。实现时先理解相关代码，再核对涉及的正式约定；需求与已确认设计决定改动目标。目录描述用途，不意味着文件会自动删除。

独立设计、补充或改进单元测试时，以 `unit-testing` 为主要工作流；为此阅读生产代码不自动叠加代码技能。功能实现和生产代码修复仍由代码技能负责，包含必要测试，需要具体测试设计指导时再参考测试技能，不要求拆成两轮或采用 TDD。测试代码审查保持静态只读；仅运行指定测试属于验证任务，不自动补测试或修复。编写测试和实际运行分别报告，运行始终遵循目标项目限制。

例如，单独补测试且保持生产代码不变：

```text
用 $unit-testing 为当前模块补充边界和失败场景的单元测试，不修改生产代码；是否运行按项目约定执行。
```

已有结论需要形成正式说明时，使用：

```text
用 $document-confirmed-design 把已确认的职责和数据关系整理成正式说明，不继续补设计。
```

普通工程问答和局部措辞修改不自动进入上述工作流。

正式文档编写中，冲突影响有效约定应如何表述时，先提出具体问题，暂停受影响内容，澄清后再继续；材料已明确区分尚未实现的目标与当前行为时直接记录。具体边界见 [正式文档技能的澄清规则](document-confirmed-design/SKILL.md#clarify-conflicts-before-continuing)。

创建或修改技能时，可以使用当前环境提供的 `$skill-creator`，说明任务、典型输入、期望输出和触发边界，并指定在本仓库中创建：

```text
用 $skill-creator 在本仓库创建 <技能名>。
处理的任务：……
典型输入和期望输出：……
应该触发和不应该触发的场景：……
遵循本仓库的命名、语言和资源组织约定。
```

修改已有技能时，说明要解决的问题和需要保留的约定。新增、重命名、移除技能或调整其用途时，同步更新上面的目录表。

修改后检查元数据、文件引用及相关说明的一致性。根据改动需要和已有授权进行行为评测，分别报告结构检查与实际行为验证；结构检查通过不代表行为评测通过。具体技能的案例和验证方法见其目录。

Codex 的接入和发现方式参见 [官方技能文档](https://learn.chatgpt.com/docs/build-skills)；仓库维护指令的加载方式参见 [AGENTS.md 文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。
